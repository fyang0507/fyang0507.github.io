### The colored-card problem, precisely
Five near-duplicate card components exist across the five pages, all slightly different, none matching the site's established tactile language:

| Class | Where used | Shape |
|---|---|---|
| `.fa-card` (+ `--wash-blue/peach/wheat`) | Overview, 2 grids | full pastel-wash background, 3px top accent border, floating dot pseudo-"pin" |
| `.fa-capability` | System, 1 grid | near-identical to `.fa-card` but independently defined, bg picked by blind `nth-child(3n+...)` cycling instead of semantic modifier |
| `.fa-contract` | Components, per-component | flat `border-top:2px solid ink`, no accent color at all |
| `.fa-demo-detail` | Demos, per-demo | same flat top-border treatment as `.fa-contract`, separately defined |
| `.fa-rail-card` | System, "operational questions" grid | left-border variant, separately defined |

This is the generic "SaaS marketing feature card" pattern (pale tint + thin accent border + decorative dot) repeated five times with drift, and it's the one part of the page that doesn't carry the site's real visual identity. **Now visually confirmed** (screenshots, §7): the Overview and System card grids do read as flat, sharp-cornered, generic-SaaS tiles when set beside Building.dc.html's tilted, pinned, drop-shadowed cards in the same browser session — the contrast is stronger live than it reads in CSS alone. Contrast with `Building.dc.html`, which has a genuinely distinctive, already-good pin/corkboard/torn-paper system (`.board-pin` SVG, `.standard-card`'s `clip-path` deckle edge, `.board-shell::before`'s washi-tape masking strip), and with `About.dc.html`'s tilting flip-card (`.field-card`, pointer-driven 3D tilt, bird sprite, spring easing). The Fred Agent chapter pages currently read like a detached microsite bolted onto that world.

**The `.fa-capability` `nth-child` cycling is a confirmed live bug, not just a code smell.** With exactly 4 capability cards on the System page, the `nth-child(3n+2)`/`nth-child(3n+3)` cycle produces: item 1 = plain, item 2 = wash A, item 3 = wash B, item 4 = plain again (the `3n+1` bucket repeats item 1). Verified both in fred-agent.css (lines 129-130) and live in the browser: PRESENCE (item 1) and RECOVERY (item 4) render in the *identical* wheat/tan tint, with no thematic reason for them to match — it's an accident of modulo arithmetic, not a design choice. This raises the priority of the card-system consolidation from "nicer" to "fixes a visible, unintentional bug."

Also found: `.fa-recipe` / `.fa-recipe--wide` (defined in `fred-agent.css`, base plain-paper card, no wash) are **dead code** — confirmed via grep across all 5 pages, nothing references them (the visually similar `.fa-recipe-grid` *is* used, just wrapping `.fa-card` items, not `.fa-recipe` items). `.fa-contract-grid--three` is also dead. Safe to fold away during consolidation rather than carry forward. `.fa-card--signature` (the proposed new class, §4) does not exist anywhere yet — confirmed unbuilt, nothing to conflict with.

**8 of the 12 flagged "signature-tier" cards carry a wash tint; 4 render bare, by two different mechanisms** (corrected count — an earlier pass of this doc only counted one of the two mechanisms and said "2 render bare"). Overview's grids contribute 2 markup-level bare cards: items 3 (line 106) and 4 (line 173, second grid) are plain `.fa-card` with **no** `--wash-*` modifier in the HTML at all — just ink border, no tint. System's capability grid contributes 2 *more* bare cards, but by the `nth-child` bug already described above, not by markup: PRESENCE and RECOVERY both fall through to the unwashed base look because they land in the `nth-child` cycle's "miss" bucket, not because their markup omits a modifier. Total: 8 washed + 4 bare (2 by absent modifier, 2 by cycling accident) of 12. The new signature-tier component needs a deliberate "no modifier" look for the first kind, and — since §4 already requires wash color to come from an explicit modifier, never `nth-child` position — the second kind stops being an accident either, so it either gets an explicit modifier or an explicit deliberate "no wash" choice.

## 4. Design plan (reasoned through, not yet built)

Framed through the frontend-design skill's process. Because Fred explicitly locked the palette/type/overall system, the actual creative freedom here is in (a) the card component and (b) motion — which is conveniently exactly what got flagged. Everywhere else (section rhythm, hero grid, reading layout, system map) is judged already good and shouldn't be touched beyond light polish, per "spend your boldness in one place" — **but that confidence isn't uniform across pages, worth being honest about (a verifier flagged this)**: Overview's hero/grid, System's hero/map, and Building.dc.html were all confirmed live in a real browser this session (§7). Principles', Components', and Demos' layouts were judged from source CSS only — never opened in a browser this session — so their "already good, light touch only" verdict is a source-read judgment, not a visually-verified one. Treat it as a working assumption to confirm, not a settled fact, when each of those 3 pages gets its visual pass in §8 step 5/6.

**Grounding metaphor**: the corkboard (`Building.dc.html`) pins *projects*; these chapter pages are the *notebook pages* behind one pinned project. Pull the board's materiality one level down — restrained, concentrated at structural moments — rather than inventing a new visual language.

### Tokens
No new hex values. Reuse `--paper/--paper-2/--ink/--soft/--mark/--mark-deep/--line-strong/--wash-blue/--wash-peach/--wash-wheat` exactly as defined. Add two easing custom properties to `fred-agent.css`'s `:root`: `--ease-open:cubic-bezier(.2,.85,.28,1.18)` (hover/interactive), `--ease-out:cubic-bezier(.16,1,.3,1)` (scroll reveals — deliberately *not* springy; a bounce on every card as you scroll a long reading page gets tiring fast, reserve the overshoot for direct hover/press feedback only).

**Naming update from the original plan**: originally proposed as `--ease-spring`. Renamed to `--ease-open` — see §5, this value is byte-identical to Building.dc.html's existing `--ease-open` token, and matching the name (not just the value) makes the two files read as one hand-built vocabulary even though they can't share a literal `:root` block.

### The unified card component (this is the main fix)
Replace all five duplicate card classes with **one shell, two tiers**:

- `.fa-card` — base shell: plain paper surface (not tinted), thin 2px top accent rule via `::before` reading a `--card-rule` custom property, border-radius, transition hooks. The `--wash-blue/peach/wheat` modifiers survive by name but now set `--card-rule`/`--card-tape` custom properties instead of a full background tint — same three hues, applied with more confidence and much better text contrast. **Must also define a sane default for no modifier present** (§3 finding: 2 of 8 Overview cards currently render bare) — not just fall through to unstyled.
- `.fa-card--signature` — the flagship tier, used **only** where Fred flagged the problem: Overview's two 4-up grids ("what changes", "choose a way in") and System's "what becomes possible" capability grid (12 cards total across 2 files, confirmed exact by direct count). Adds: a whisper of per-card rotation (`±0.4–0.6deg` via `nth-child`, resets to 0 on hover — "pinned loosely"), larger padding/type, hover = lift + un-rotate + shadow grow on `--ease-open`. **Wash color must be assigned by explicit semantic modifier class, never by `nth-child` position** — this is now a confirmed-bug fix, not just a taste call (§3). **No tape-corner flag on this tier** — dropped after the design-guide cross-check (§6); tape stays a rare hero-moment device (2 uses total sitewide, both on Building.dc.html's two singular cards), not something to multiply across a repeated grid.
- `.fa-card--label` — the quiet/dense tier, used for the reference-data grids that repeat many times per page: Components' contract cards, Demos' demo-detail cards, System's operational-questions rail cards (~29 cards total). No rotation, no hover-lift (they're static reference text, not interactive — a hover affordance on non-clickable dense cards is a false signal), just the accent rule + `paper-2` surface + the existing mono-uppercase label heading style. Filed flat like index cards in a drawer, not scattered like notes on a board — that distinction (loose/editorial vs. filed/precise) is deliberate and worth keeping.

Explicitly rejected: full torn/deckle `clip-path` edges on every card, and (after §6) a tape-corner flag on every card. Building's board uses both devices sparingly — deckle-edge only on its plainest, fixed-content cards, tape only on its two most singular cards — never as a per-item grid ornament. Fred Agent's signature cards also carry a kicker + heading + paragraph + sometimes a link, so a jagged clip-path risks actually clipping descenders/wrapped lines at some viewport width. Rotation + wash + hover-lift alone still carries the "hand-placed" read without either extra device.

**CSS specificity note for whoever implements this**: hover state and reveal-visible state both want to set `transform` on `.fa-card--signature`. Don't write two competing whole-property `transform` rules (`:hover{transform:...}` vs `.is-visible{transform:...}`) — corrected mechanism (a verifier caught the original wording here misstating this): a pseudo-class and a class carry *equal* specificity, so `.fa-card--signature:hover` and `.fa-card--signature.is-visible` tie, and whichever rule is declared later in the stylesheet wins by source order alone — fragile and easy to invert by innocently reordering rules later. Compose the transform from custom properties instead, so hover and reveal-progress can both be "true" at once and no ordering dependency exists:

```css
.fa-card--signature{
  --tilt:0deg; --reveal-y:0px; --hover-y:0px; --hover-r:var(--tilt);
  transform:translateY(calc(var(--reveal-y) + var(--hover-y))) rotate(var(--hover-r));
  transition:transform .3s var(--ease-open),box-shadow .3s var(--ease-open),opacity .6s var(--ease-out);
}
/* per-card whisper of rotation — a verifier caught that this was described in prose but never actually
   written as a rule in the original draft; ±0.4–0.6deg, deliberately not a symmetric alternation */
.fa-card--signature:nth-child(4n+1){--tilt:-0.5deg}
.fa-card--signature:nth-child(4n+2){--tilt:0.4deg}
.fa-card--signature:nth-child(4n+3){--tilt:-0.45deg}
.fa-card--signature:nth-child(4n+4){--tilt:0.55deg}
.reveal-ready .fa-card--signature.fa-reveal{--reveal-y:18px;opacity:0}
.reveal-ready .fa-card--signature.fa-reveal.is-visible{--reveal-y:0px;opacity:1}
.fa-card--signature:hover,.fa-card--signature:focus-within{--hover-y:-4px;--hover-r:0deg}
```
(`nth-child(4n+…)` assumes each signature grid is exactly 4-wide, true for both current uses — Overview's two grids and System's capability grid are all 4-up. If a future grid uses a different column count, recheck the modulus rather than assuming 4 still applies.)

### Motion system

1. **Scroll reveal** (`.fa-reveal` utility): IntersectionObserver-driven, `opacity:0/translateY(18px) → 1/0` on `.is-visible`. Guard against flash-of-invisible-content with the standard "armed class" pattern — CSS only hides `.fa-reveal` elements when a `.reveal-ready` class is present on `<html>`, and that class is only ever added by JS once it has successfully set up the observer. If JS fails/is blocked, `.reveal-ready` never appears, so `.fa-reveal` elements simply render normally (visible, static) — no dependency on JS for baseline correctness. Stagger within a grid row is handled in pure CSS via `nth-child` → `transition-delay` (no need for per-element JS timing, since IntersectionObserver fires all four cards in a row on basically the same tick and the CSS delay staggers the *visual* start).
   ```js
   var reducedMotion = window.matchMedia('(prefers-reduced-motion: reduce)');
   var revealObserver = null;
   function initReveals(){
     if (reducedMotion.matches || !window.IntersectionObserver) return;
     document.documentElement.classList.add('reveal-ready');
     if (!revealObserver) {
       revealObserver = new IntersectionObserver(function(entries){
         entries.forEach(function(entry){
           if (!entry.isIntersecting) return;
           entry.target.classList.add('is-visible');
           revealObserver.unobserve(entry.target);
         });
       }, {rootMargin:'0px 0px -6% 0px', threshold:0.1});
     }
     Array.prototype.forEach.call(document.querySelectorAll('#dc-root .fa-reveal:not([data-reveal-bound])'), function(el){
       el.setAttribute('data-reveal-bound', '');
       revealObserver.observe(el);
     });
   }
   ```
   Call this at the same lifecycle points `initSystemMaps()` already gets called (initial `observeRenderedPage()`, and again after each chapter swap) — it's idempotent via the `data-reveal-bound` marker, so calling it from the existing MutationObserver-driven init path is safe.

   Considered and rejected: pure-CSS `animation-timeline:view()` scroll-driven animations (no JS at all, `@supports`-gated). Elegant for single elements, but doesn't stagger a horizontal row of cards predictably (percentage-based `animation-delay` along a view-timeline behaves differently from wall-clock delay, and browser support is still uneven). IntersectionObserver + CSS `transition-delay` is the boring, reliable choice — use it.

2. **Chapter transitions**: wrap the existing fetch-swap navigation in `fred-agent.js`'s `navigate()` with the View Transitions API, feature-detected, skipped entirely under reduced motion:
   ```js
   var canAnimate = !reducedMotion.matches && typeof document.startViewTransition === 'function';
   if (canAnimate) document.startViewTransition(performSwap); else performSwap();
   ```
   where `performSwap` is the existing body of the `.then()` handler (validate `nextStage`/`currentStage` *before* this branch, not inside the VT callback). Scope the transition to the content region only — not a whole-page crossfade that would visually double the (unchanged) header/nav — by giving `#main-content.fa-stage` a `view-transition-name` in CSS.

   **Interaction with `.fa-rise` a verifier caught and this draft now accounts for**: every chapter's `<main id="main-content" class="fa-stage fa-rise">` is static in the source HTML, so `fetchChapter()` → `DOMParser` → swap (fred-agent.js:107-122) inserts a *brand-new* node carrying `fa-rise` on every SPA navigation today, already — meaning `.fa-rise`'s own entrance animation (opacity 0→1, translateY 14px→0) already replays on each chapter swap, independent of anything proposed here. If the View Transition CSS below also animated the *new* side's opacity/position, the two would compound into a visibly doubled entrance. Fix: let the View Transition own only the *outgoing* content's exit, and explicitly cancel the browser's own default crossfade-in on the incoming side, leaving `.fa-rise` — already working, unchanged — as the sole entrance animation:
   ```css
   #main-content.fa-stage{view-transition-name:fa-main}
   ::view-transition-old(fa-main){animation:fa-vt-out .3s var(--ease-out) both}
   ::view-transition-new(fa-main){animation:none}
   @keyframes fa-vt-out{to{opacity:0;transform:translateY(-8px)}}
   @media(prefers-reduced-motion:reduce){::view-transition-old(fa-main){animation:none!important}}
   ```
   `::view-transition-new(fa-main){animation:none}` overrides the browser's default fade-in for that pseudo-element (author styles beat the UA stylesheet), so the incoming `<main>` simply appears at full opacity the instant the new phase starts, and `.fa-rise` — already on that node, already correct — handles the actual entrance motion exactly as it does today. Net effect: old content fades and lifts out via the View Transition, new content fades and rises in via the pre-existing `.fa-rise`, and neither doubles the other.

   (The explicit reduced-motion override here is belt-and-suspenders on top of the JS feature-check — see the wildcard-doesn't-reach-view-transitions caveat above.) This is the headline "transitions.dev-inspired" deliverable: a real page-transition choreography, implemented natively, zero new dependencies.

3. Hover physics on interactive elements (`.fa-card-link` arrow, `.fa-card--signature`, `.fa-system-step`) move from the current flat `translateY(-1px)` to `--ease-open`-based lift, consistent with the rest of the site.

### Card system rebuild (Fred rejected the first version, then picked a synthesis)

Fred's rejection, verbatim: *"the color boxes. The 3D shading makes the cards look like tilted, and the added top line doesn't fit the rounded edge at all. And the hover effect is inconsistent, some applied, some didn't."* Confirmed all three precisely before doing anything else, not just taken on faith:

- **Top line vs. rounded corner**: zoomed screenshot of the original `.fa-card::before` (a `border-radius:14px` request on a 2px-tall bar) showed exactly the predicted failure — the bar's corner renders square while the card's own border, which has real height to work with, renders a genuinely smooth curve. A real geometry bug, not a taste call.
- **Box-shadow "3D tilt"**: `box-shadow:3px 4px 0 rgba(...)` — hard-edged, zero-blur, offset duplicate-shape shadow, the flat-design "sticker" trope. Combined with the signature tier's whisper of rotation, it amplified into the tilted look.
- **Hover inconsistency**: `.fa-card--signature` had hover, `.fa-card--label` deliberately didn't (original design intent: static reference cards shouldn't imply clickability) — sound reasoning, but reads as broken to someone scanning a page with both tiers present.

Fred asked why this wasn't done with a team the way the earlier page rollout was — fair, since this is exactly the kind of task (rejected design, need real alternatives, not one more solo guess) a team suits better than solo iteration. Dispatched 3 parallel fresh agents, each with a different creative brief and the same confirmed-bug diagnosis, told not to touch any repo files — proposal-only, CSS + rationale as their return value:

- **Minimal/restraint**: moved the accent onto the card's own `border-left` (no second shape, so no second radius to clash), cut the shadow to nothing-at-rest + the sitewide soft `--shadow` token on hover only, cut rotation entirely, gated hover on `:has(.fa-card-link)` so only cards that actually link somewhere respond — grepped real markup and found today's hover *already* over-fires (all 10 signature cards on Overview lift, only 4 contain a link), a finding this proposal fixed as a side effect.
- **Editorial/typographic**: moved the accent off the card entirely onto a short underline beneath just the kicker word (sized to the text, inset in padding — nowhere near the corner at all), no shadow ever, no rotation, hover keyed to real interactivity. Self-flagged its own gap honestly: its hover selector (`a.fa-card:hover`) assumed the whole card is an anchor, which doesn't match the real markup (`<article>` wrapping a separate `.fa-card-link`) — would have matched nothing as shipped; corrected before use.
- **Tactile/paper**: grounded in `Building.dc.html`'s actual working code (`filter:drop-shadow()`, not `box-shadow`; clip-path shapes with no border-radius of their own). Kept rotation, replaced the top bar with a small washi-tape accent (own silhouette, can't clash with the card's corner) on signature cards and an inset edge stripe (cleared by exactly `--radius` on each end) on label cards. Hover differs by tier on purpose — signature lifts and un-rotates, label only shifts color in place — rather than by link presence.

Built a real side-by-side comparison rather than deciding from the three written rationales — a self-contained HTML page using the site's actual tokens and real page content (Overview's Time/Reach cards, Components' Sundial contract cards), all three proposals live and independently hoverable, published as an Artifact and verified directly (zoomed into every corner, confirmed no clash in any of the three, tested hover on link-bearing and non-link cards in each column). This is also where the editorial proposal's broken hover selector got caught and fixed for a fair test, and where a genuine three-way convergence became visible: minimal and editorial independently arrived at "cut rotation entirely," while tactile (the one proposal actually briefed to explore materiality) kept it.

**Fred's pick**: signature tier = tactile, label tier = minimal + an added hover (tactile's label tier already had one; minimal's didn't). One issue Fred caught from the live comparison: the tape's rotation ran noticeably larger than the card's own tilt (±2–3° vs. the card's ±0.4–0.55°) and pivoted around its own center, which read as visually imbalanced rather than gently placed. Fixed by reducing the tape's rotation range to ±1–1.2° (proportionate to the card's own tilt instead of 5–6× larger) and moving `transform-origin` to `50% 85%` (near where the tape overlaps the card) so it reads as anchored at that point rather than spinning freely.

Final synthesis, implemented in `fred-agent.css`:
- **Signature tier**: tactile's CSS as proposed, with the tape-balance fix above. `border-left` reset to neutral (`1px solid var(--line-strong)`, matching the other three sides) since the tape is now the sole accent device — a leftover colored border would have competed with it.
- **Label tier**: minimal's flat `border-left`/no-rotation structure, plus a hover rule that didn't exist in the original minimal proposal — background shifts toward `--paper-3`, the three *neutral* border sides darken toward `--ink`, soft `--shadow` appears. The colored left edge (`border-left-color`, still reading `--card-rule`) is deliberately left out of the hover rule — darkening all four sides together would have made the category-color accent disappear at exactly the moment someone's looking at the card.

Verified live post-implementation (hard-reloaded, both pages): Overview's signature cards — tape now sits close to level at rest, zoomed screenshot confirms; hover visibly un-rotates and shadow deepens. Components' label cards — border-left accent intact, hover deepens background/border/shadow while the colored edge holds its color, zoomed screenshot confirms clean corners on both the resting and hovered state. Zero console errors on both pages. Cache-busting `?v=` bumped to `20260721-2` on `fred-agent.css` across all 5 pages that load it.
